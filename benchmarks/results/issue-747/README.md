# Issue #747 (slice 1): `LEVEL` above 99 selects level 1, as in ngspice-47

#747 lists corpus-g decks that spice-ts rejected with `uses unsupported model LEVEL=<n>` while
ngspice-47 runs them unchanged. For `LEVEL=260` (Xyce's EKV 2.6), `LEVEL=102/103` (PSP) and
`LEVEL=504` (MEXTRAM) the reason is not an EKV/PSP/MEXTRAM model in ngspice-47: it has none of them.
ngspice-47 prints, for each such card:

```
Illegal value for level.
Level must be < 99 (Setting Level to 1)
```

and simulates level 1 (MOS1 for nmos/pmos, Gummel-Poon for npn/pnp). The rule is INPfindLev in
`src/spicelib/parser/inpfindl.c`: the level is rounded to `(int)(level + 0.5)`, and a value below 0
or above 99 is replaced by 1. INPdomodel (`inpdomod.c`) uses it for `npn/pnp`, `njf/pjf`,
`nmf/pmf/nhfet/phfet`, `nmos/pmos/nsoi/psoi` and `r`; level 0 shares `case 1` in each of those switches.
Diode cards do not go through INPfindLev, so the `D` decks with `level=200`/`2002` (JUNCAP200,
DIODE_CMC) are unaffected.

spice-ts now applies the same rule in `parseModelCard` (`packages/core/src/parser/model-parser.ts`)
and reports a parse warning naming the model and the written level. In-range levels that spice-ts does
not implement (MOSFET `LEVEL=7`, `10`, `54`, `99`, ...) still raise `UnsupportedModelLevelError`.
No MOS1 code and no MOSFET level dispatch changed.

A native EKV 2.6 port (#4) cannot be checked against ngspice-47, and on this deck it would move
spice-ts away from the ngspice-47 result. It needs a different reference (Xyce, or the EKV Verilog-A
model through OSDI) and stays open, as does the rest of #747 (B3SOI `LEVEL=10`).

  spice-ts rejects the MEXTRAM-only `DTA` parameter on a Gummel-Poon card, which ngspice-47 accepts.
  That is a separate BJT parameter gap, not a level issue.

## Unit tests against ngspice-47

`packages/core/src/parser/model-level-limit-747.test.ts` reads the decks in `decks/` and the
references in `references/` (generated by `generate-references.ts` from the same bytes; the test checks
each deck's SHA-256 and that ngspice-47 printed the level notice):

| Deck | Analysis | Worst error vs ngspice-47 |
|---|---|---|
| nmos-dc-level260.cir | DC sweep, NMOS LEVEL=260 with body bias | 9.2e-16 relative, I(VD) |
| cs-amp-ac-level260.cir | AC, common-source NMOS LEVEL=260 | 2.0e-8 relative, v(out) |
| cmos-inverter-tran-level260.cir | TRAN, default LEVEL=260 cards (as in the corpus deck) | 2.3 mV of 3 V, v(out) |
| npn-op-level260.cir | OP, NPN LEVEL=260 (Gummel-Poon) | 3e-8 relative, v(b)/v(c) |

The same file pins that `LEVEL=100`, `260`, `1E3` and `-3` produce bit-identical results to `LEVEL=1`,
that `LEVEL=0` and `1.4` select level 1 and `1.6` level 2, that a `.model` inside `.subckt` gets the
same fallback and warning, and that `LEVEL=7` and `LEVEL=99` still raise `UnsupportedModelLevelError`.
