# spice-ts 0.4.0 — release candidate

Release target: 17 October 2026. This is the first release since npm 0.3.0
(10 June). These notes describe the candidate, not a published package. Package
versions remain unchanged here; Mattia owns versioning, publication and tags.

## More real decks, fewer silent approximations

The main change is ngspice compatibility across parsing, nonlinear devices and
transient integration. PULSE/PWL breakpoint scheduling, UIC and initial-condition
handling, device temperature and multiplicity, source/ground conventions, and
sparse real/complex solves have all received correctness work. Vendor libraries
benefit from scoped subcircuit models and parameters, forward F/H source
references, behavioural E/G sources and branch-current expressions, PSpice
functions, RES/VSWITCH/ISWITCH forms, and more ngspice/Xyce card spellings.

Device coverage now includes MOS levels 2/3/6/9, BSIM1/2, bounded BSIM3
3.2.x/3.3 and BSIM4 with geometry-bin selection, expanded Gummel–Poon BJT and
bounded NPN/PNP VBIC temperature/charge/delay support. Transmission-line work
includes lossless T-line electrical length, LTRA controls and uniform distributed
RC (U/URC) ladders. VDMOS supports thermal nodes. XSPICE includes digital gates,
ADC/DAC bridges, D/JK flip-flops, triangle and oneshot models; this is not blanket
support for every XSPICE code model or every transistor parameter.

Analyses and results extend beyond OP/DC/AC/TRAN: bounded noise, distortion,
transfer-function, pole-zero, sensitivity and S-parameters; `.control`
`linearize`, `fft` and `psd`; temperature/parameter sweeps. Native repeated
analyses are retained in `SimulationResult.analyses`, while legacy last-per-type
fields remain available. Read each analysis/backend's documented limits rather
than assuming full ngspice language coverage.

## Agent and embedded workflows

The MCP package adds circuit-json simulation input, bounded `spice_convert` and
`spice_measure` tools, advisory topology warnings in `spice_validate`, and
structured errors with actionable details. Streaming jobs have a per-server
concurrency quota (default two), bounded result batches, cancellation and
five-minute terminal-job retention. Clients should inspect `spice_capabilities`
instead of assuming every tool/backend accepts every circuit.

The protocol and WASM packages provide a versioned request/result contract. The
numeric WASM backend supports a bounded linear subset, not the full native
simulator. The packed-package smoke test checks a real WASM RC AC solve, not just
an import. UI accepts core `^0.3.0 || ^0.4.0`; the planned UI release is 0.3.1,
not the accidental peer-triggered 1.0.0. Core and MCP are planned for 0.4.0.

## Behaviour changes — check existing decks

- Unsupported MOS levels now raise `UnsupportedModelLevelError` instead of
  silently running level 1. Unsupported BSIM3 versions/non-quasi-static modes
  are rejected rather than silently approximated.
- A model declared inside `.subckt` is local, not global last-definition-wins.
  X-line `m=` and current-source/device multiplicities are no longer ignored.
- Temperature expressions are re-evaluated at each sweep point. PSpice
  model-temperature keys have explicit translations and unsupported cases fail;
  a previously ignored field may therefore change a result or produce an error.
- Time grids can change: PULSE defaults, accept-time breakpoints, TSTART output
  omission, UIC's missing t=0 row, and Newton retry/order control follow ngspice
  more closely. Compare interpolated waveforms, not array indices.
- Several malformed/inert card forms are now ignored with ngspice-style parser
  warnings; known-but-unimplemented features still produce structured errors.
  Check warnings instead of interpreting successful parsing as complete support.

## Then versus now

The bounded release comparison uses the same current classic/aggregate adapters
for npm core 0.3.0 and the candidate, with byte-identical, hash-checked inputs:
20 fixtures each from ngspice, classic, Xyce, corpus-d and corpus-e. Sources,
licences and unchanged fixture manifests are recorded in
[benchmarks/SOURCES.md](../../benchmarks/SOURCES.md). The 100 entries include
repeated circuits across corpora; they are not 100 independent circuit designs.
No corpus f–n, upstream-bug, Xyce-mutual or vendor-wide refresh is claimed here.

One frozen-corpus run per engine; the scaling matrix uses three fresh-process,
interleaved repeats per engine/cell, no warmups, with median adapter wall times.
Core timing includes the current harness's parse precheck, simulation and result
mapping; ngspice timing includes its subprocess and raw-file parsing. Each child
has a 120-second wall-clock bound and a 4 GiB V8 heap bound. All scaling decks add
the same `.save` probe to bound ngspice raw output. ngspice uses its default
solver, not a tuned per-deck solver. This is a shared-host cold-start comparison,
not a statistically isolated solver microbenchmark.

“Matched” requires successful runs on both engines, paired plots, at least 95%
of target-grid points aligned and every compared signal within 1e-6 absolute OR
1% maximum relative error. One global policy, no circuit-specific tolerances;
relative errors exclude references below 1e-15. The current aggregate adapter
uses common signal names within paired plots, so this is not a guarantee that
all engine-specific vectors are covered. Run-success is not correctness.
Worst errors below are matched-point maxima across all comparable rows,
including losing rows, not only rows passing the policy.

Measured on Apple M5 Pro, darwin arm64, Node v22.23.1, ngspice-47; candidate
simulator code at `525dafca` (release preparation changes no simulator behaviour).
The raw per-signal JSON and commands accompany the preparation card/PR.

## Known losses and release gates

- No baseline-success → candidate-failure or baseline-match → candidate-loss
  transition was observed in the 100-fixture run. This does not erase existing
  losses: 21 of the 52 jointly successful fixtures still fail the matching policy,
  including HFET, Jimi fuzz, MOS/BJT transient and lossy-line cases. Candidate
  worst voltage error is 2.716 V on Jimi fuzz; 31 fixtures remain unsupported
  and the mixer-distortion fixture still fails to produce a runnable analysis.
- Small workloads are slower: RC 1k is 2.07× slower than 0.3.0
  ([#1204](https://github.com/mfiumara/spice-ts/issues/1204)); mesh 1k is 2.42×
  slower ([#1205](https://github.com/mfiumara/spice-ts/issues/1205)). ngspice is
  still faster on RC at every tested size, mesh 1k and CMOS 1k.
- Single cold corpus samples also take longer on the candidate: MOS6 chain
  (both corpus aliases, [#1206](https://github.com/mfiumara/spice-ts/issues/1206)),
  MOS6 simple inverter ([#1207](https://github.com/mfiumara/spice-ts/issues/1207))
  and Jimi fuzz ([#1208](https://github.com/mfiumara/spice-ts/issues/1208)).
  These are timing observations needing repeated profiling, not proven stable
  throughput regressions; their accuracy improved. Median baseline/candidate
  ratio across those four entries is 0.216×. Across the 52 jointly successful
  candidate/ngspice entries, median ngspice/candidate ratio is 0.0834×; neither
  statistic describes the unsupported population.

These measurements do not establish universal parity or speed superiority.
A fresh nightly aggregate refresh on the exact release-candidate SHA, green
required CI and independent exact-SHA review are separate release gates; this
lean comparison does not replace them. The aggregate's existing provenance pin
is stale on the starting tree and its six accounting tests fail; this PR does
not re-pin stale outcomes or present them as refreshed evidence.

## ngspice defects found during compatibility work

Independent invariants also caught upstream defects; ngspice output is not an
oracle when it violates those invariants:

- [ngspice #877](https://sourceforge.net/p/ngspice/bugs/877/): HFET1 instance
  current changes with netlist order because an inverse flag is not reset.
- [ngspice #878](https://sourceforge.net/p/ngspice/bugs/878/): the analogous
  MESA order-dependence defect. spice-ts keeps each device's state independent.
- [ngspice #880](https://sourceforge.net/p/ngspice/bugs/880/): whole-number
  `.options` values above INT_MAX can narrow on arm64; `rshunt=1T` becomes
  2147483647, making the shunt about 466 times too strong. Platform/compiler
  dependent; not a general result about every ngspice build.

These are SourceForge ticket numbers, not spice-ts GitHub issue numbers.
See [the upstream-bug corpus](../../benchmarks/corpus/ngspice-bugs/README.md)
for the independent-oracle methodology; the full upstream suite was not rerun
for this release-preparation slice.

Reproduce: install npm `@spice-ts/core@0.3.0` into a clean scratch prefix, build
this checkout, then run `spice-heavy pnpm exec tsx
benchmarks/release/then-vs-now.ts --baseline <prefix>/node_modules/@spice-ts/core/dist/index.js
--output <scratch-results>`. Use `--summarize <scratch-results>/report.json` to
render the headline table without rerunning engines. Packaged-consumer check:
`pnpm -r build && node benchmarks/release/packed-smoke.mjs`.
